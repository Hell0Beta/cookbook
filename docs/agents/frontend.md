# Frontend Agent

## What you own

Everything in `apps/web/` — the entire user-facing surface of the app. You build the bento design system, every screen, the unified block-based recipe reader/editor, and all client-side state (timers, shake gesture, query caching).

  - §2 Design System (bento grid, 4–6px radius rule, color tokens, typography, core components, iconography)
  - §3 Screens (Dashboard, Search, Recipe Reader/Editor, Quick Add modal, Meal Planner, Grocery List, Profile)
  - §4 Key Interaction Flows (multi-recipe reader, quick add, Notion-style editing, servings scaling, YouTube import UX, tag filter panel, ingredient search UX)
  - §5 Empty/Loading States

  - §7 "Recipe Reader/Editor, Quick Add, Timer & Shake Gesture" (implementation approach for your hardest components)
  - §11 API Surface (every endpoint you'll consume, including the `llm_quota_exceeded` error convention for AI-dependent endpoints)
  - §13 Open Questions (responsive web PWA resolved per §0)

Use this to build the Tailwind theme.

## Scope

- Tailwind config + CSS variables implementing the Heirloom Kitchen tokens (design.md §2 mapped to concrete values). **Fonts self-hosted via `next/font/local`** (Plus Jakarta Sans, Work Sans, JetBrains Mono) — no Google Fonts CDN, no external requests at runtime (development.md §0).
- Bento primitives: base `BentoCell` component (image/text/action regions, 1x1 / 2x1 / 2x2 spans, 6px radius, 1px border, diagonal-hatch placeholder), plus the components built on it (design.md §2.4 #5–#9).
- Screens per design.md §3: Dashboard, Search (with Filter Tag Panel), Recipe Reader/Editor, Quick Add modal, Meal Planner (3-panel), Grocery List, Diet Preferences/Profile.
- The unified read/edit surface (design.md §3.3, development.md §7.1): one component per block type with `readonly`/`editable` props — never two component trees. BlockNote as the starting point; spike the custom `Step` block (inline timer chip) before committing (development.md §2, "Block-style editor").
- Client state: Zustand store for the global timer tool (multiple concurrent timers keyed by `(recipe_id, step_id)`, single interval ticking the store — development.md §7.3), shake-to-advance via `DeviceMotionEvent` with iOS permission prompt (§7.4).
- Data layer: TanStack Query hooks for every endpoint in development.md §11. All request/response types imported from `packages/shared`.
- Servings stepper with live scaling display (design.md §4.4) — the math comes from the backend (`GET /recipes/:id/scale`) or `packages/shared` scaling helpers owned by integrations; you render it.
- Quick Add modal (design.md §3.4, development.md §7.2) — same component parameterized by `recipe_id`, triggered from Recipe Reader and Search result cells.
- **AI quota alert UI** (design.md §5, development.md §0/§11): when an endpoint returns `llm_quota_exceeded` (or `quota_exhausted: true`), show the dismissible "daily AI requests used up" banner and grey out only AI-dependent entry points (YouTube import, Discover). All other features keep working; never a blocking error screen.

## Explicitly NOT your job

- **API route handlers / business logic** — backend agent owns `apps/api/`.
- **Schema/type definitions** — import from `packages/shared`. If a type is missing there, add it to `packages/shared` (that part you may do) rather than declaring it locally in `apps/web`.
- **Tagging, YouTube extraction, recommendation logic** — ai-pipeline owns it; you consume endpoints.
- **Unit conversion / ingredient parsing math** — integrations owns it. You call `GET /recipes/:id/scale` and the grocery-list endpoints.
- **Prisma schema / migrations / auth server side.**
- Updating `docs/design.md` or `docs/development.md` unless a spec conflict is genuinely unresolvable — in that case flag it and record the decision in "Decisions" below.

## Key implementation notes (from development.md)

- Block editor: model the recipe client-side as an ordered array of typed block objects; persist via a single `PUT /recipes/:id/blocks` batch update on save/blur — never one request per keystroke (§7.1).
- Timer state must live in a global store, not per-component, because the floating timer pill survives navigation (§7.3).
- dnd-kit for block reordering AND for dragging recipes onto calendar days (§2).
- Use FullCalendar's external-event-dragging for the planner, or spike a hand-rolled CSS grid + date-fns week view first (§2, "Meal Planner calendar").
- The Quick Add modal's slot mode needs the "next occurrence" preview — backend exposes the resolution as a pure function via `packages/shared` so you can show "adds to: Today's Dinner" before confirming (§7.2).
- React Hook Form + Zod for the Quick Add modal, diet profile, manual recipe fields; reuse Zod schemas from `packages/shared` (§2, "Forms & data").
- **Offline-first (§0):** the web app itself must make zero network requests except to the API on the homeserver — fonts, icons, images all bundled/local. Bundle everything at build time so the app works with the internet down (only LLM/import features fail gracefully).

## Decisions

- **Block editor: hand-rolled, not BlockNote** (Phase 1). The spec's block types are deeply custom (quantity/unit/role-pill ingredient rows, timed steps, servings-stepper meta), so a single component per block type with `readonly`/`editable` props was built directly on dnd-kit. Revisit BlockNote only if generic rich-text needs emerge. Implements development.md §7.1's actual requirement (same component tree in both modes).
- **Fonts: `@font-face` + vendored woff2 in `public/fonts/`** with system-stack fallback (globals.css). Drop the variable woff2 files in at setup — no CDN at runtime per development.md §0, and no build-time fetch either.
- Tailwind v4 (CSS-first `@theme` tokens in globals.css, no tailwind.config). Token names map 1:1 to design.md §2.2 / Heirloom Kitchen.
- **Tailwind v4 var shorthand is parens, not brackets** (2026-08-30). `p-[--token]` (v3 style) compiles to invalid CSS (`padding: --token`) in v4 — the UI rendered unstyled until every occurrence was rewritten `p-(--token)`. Write `foo-(--token)` for token arbitrary values; only explicit forms like `text-[length:var(--x)]` keep brackets.
- **Token fidelity pass vs. the Stitch mockups** (2026-08-30): added `--color-page: #fdf8f2` (warm cream body bg — mockups put `bg-warm-cream` on body, cells are `#fff8f5`), `--color-surface` is now `#fff8f5` (not white), added `--color-secondary-fixed`/`--color-on-secondary-fixed`, `--text-mono` (label-mono 11px JetBrains Mono) so meta rows are `font-mono text-mono`, and a `no-scrollbar` utility for chip rows. Dashboard rebuilt to the mockup structure (hero upcoming-meal cell, planned-today 3-slot row, weekly-planner summary, dashed quick-add) with design.md §5 empty states until the planner lands in Phase 5; search screen now has live title/Under-30m filtering (tag chips + Filter Tag Panel await Phase 3/8).
- **Timer Tool = React context in Providers, not per-page state** (bugfix round post-Phase 2): `TimerProvider` (components/timer/timer-provider.tsx) wraps `{children}` inside QueryClientProvider, so timers survive client-side navigation per design.md §3.3.2. State is `Map<stepId, ActiveTimer>` in a ref-driven 1s interval; `alertDone()` does 3 WebAudio beeps + `navigator.vibrate`, both try/catch (autoplay policies / unsupported browsers must not crash). The floating turmeric pill docks `bottom-24` above the tab bar; "return to step" navigates `/recipes/:id#step-<blockId>` and RecipeEditor hash-scrolls on mount + hashchange. Step chips render timer state in `StepBlockView` (idle → start; running/paused/completed variants); `recipeId` is threaded `RecipeEditor → SortableBlock → StepBlockView` and timers only arm in read mode.
- **Save re-sync + real error surfacing** (bugfix round post-Phase 2): `saveMutation.onSuccess` overwrites local `blocks/title/description` from the server response (empty blocks dropped + renumbered server-side disappear immediately instead of fighting the next save); `onError` shows the API's actual message via `ApiRequestError` — the old generic toast made Zod 400s look like opaque failures.
- **Cover art picker: gallery / camera / icon library** (2026-08-30). `CoverPickerModal` (components/cover-picker.tsx) is a bottom sheet opened from the editor's cover slot (edit mode only; picked covers save with the Done toggle like every other edit). Gallery and camera are two hidden file inputs — the camera one carries `capture="environment"`, which opens the camera on mobile and falls back to the file picker on desktop; files upload via `api.uploadImage` (POST /images, raw body + content-type). The icon library is the owner-provided Icons8 food set vendored at `apps/web/public/icons` (55 PNGs) with a hand-kept manifest in `src/lib/icon-library.ts` — drop files in, add a line. Icon covers store the static path `/icons/<file>` directly in `hero_image_url` (no upload/copy), detected by the `/icons/` prefix. `RecipeCover` is the single shared cover renderer (reader cover + recipe-card/search thumbs): photos `object-cover`, icons centered `size-8` on `surface-container` (they're 30px PNGs — never stretch them), null → hatch. Known wrinkle: a picked-then-abandoned upload leaves an orphan file in DATA_DIR/images; acceptable at ≤5 users, revisit with a sweep job if storage matters.
- **API-served images must go through `apiAsset()`** (bugfix 2026-08-30): `hero_image_url` values like `/images/<file>` resolve against the WEB origin in an `<img src>` and 404 — MealDB heroes (and any uploaded cover) looked broken. `apiAsset(path)` in lib/api.ts prefixes `NEXT_PUBLIC_API_URL` for `/images/*` and passes everything else through; `RecipeCover` applies it centrally. GET /images needs no auth, so plain `<img>` tags work cross-origin.
- **Icon library regrouped (user request 2026-08-30)**: 138 Icons8 PNGs now in `public/icons` — the `-30` files are the black-and-white set, `-48` the colored set. `icon-library.ts` carries `{file, label, category, variant}` entries grouped into food categories (meat & seafood, dairy & eggs, produce, bakery, desserts, dishes, drinks, cooking, other); `CoverPickerModal` renders one sticky-headed section per category with mono icons first, colored after. Colored icons render `size-10` (also in `RecipeCover`, detected via the `-48` filename). Adding icons = drop files in `public/icons` + add manifest entries.
- **Block text wraps; fields auto-grow (user request 2026-08-30)**: read mode used to render step/note/ingredient text in single-line `<input>`s — long text scrolled horizontally instead of wrapping. `InlineInput` now takes `readOnly` (renders a `whitespace-pre-wrap` div — wrapped plain text, no scrolling) and its `multiline` path is an `AutoTextarea` that re-fits `scrollHeight` on every render, so edit-mode fields grow to fit wrapped content with no inner scrollbar. All three block types pass `readOnly={!editable}`; ingredients are multiline in edit too.
- **Phase 5 meal planning (design.md §3.1, §3.3.1, §3.4, §4.1)**: `QuickAddModal` (components/quick-add-modal.tsx) is the single add-to-meal surface — parameterized by `recipe_id`, opened from the Reader toolbar ("Add to meal", read mode only) and from a CalendarPlus affordance on every Search result cell. Every row previews "adds to: <label>" via the shared `resolveQuickAddTarget`, so what the modal shows is exactly what the API persists; the "In next [X] minutes" row is a stepper (±5, 5–1440) with its own Add button, and "Open full planner →" routes to /planner. The Dashboard's Upcoming cell is now query-backed (`GET /meal-plans/upcoming`, "N dishes" badge when >1) and the 3-slot day row shows the first dish's cover + a "+N" badge, routing into the Reader with `?upcoming=1` / `?date=&slot=` occasion params. The Reader (recipes/[id]) consumes those params: it fetches all dishes for the occasion and renders the §3.3.1 tab strip under the app bar ONLY when >1 distinct recipe (hidden for single-dish); switching tabs swaps the whole `RecipeEditor` via a React `key`, and tabs whose recipe has a running timer show a turmeric dot (timers are already global via TimerProvider, so scoping is per-active-tab by construction). Deficiency accepted: entering the Reader with an occasion whose first dish differs from the URL's recipe id defaults to the URL's recipe if it's in the occasion, else the first tab.
- **YouTube import panel (Phase 4, design.md §4.5)**: `YouTubeImportPanel` (components/youtube-import-panel.tsx) sits at the top of `/recipes/new` above the MealDB panel. Paste → `api.importYoutube` → the DRAFT pre-fills the editor below via a keyed remount (`/recipes/new/page.tsx` is now a client component holding `initial` state + `editorKey`; RecipeEditor re-initializes from new props instead of merging into existing state). Nothing saves until the user hits Done (§5 step 5). `existing_recipe_id` responses route to the saved recipe instead of duplicating. Loading state warns about the free-tier wait; `no_recipe_content` errors toast with a "you can still type it in below" nudge; quota errors flow through `quotaAwareOnError` → the daily-AI banner. The "YouTube" source badge in MetaBlockView predates this (SourceType enum) — nothing new needed there.
- **Phase 6 Meal Planner (design.md §3.5, `planner/planner-client.tsx`)**:
  - **Calendar: hand-rolled `grid-cols-7` week strip, not FullCalendar** — the mockup (`meal_planner_empty_state/code.html`) is a day strip, FullCalendar is a heavy dep that fights the bento look, and dnd-kit is already vendored (the "calendar spike" todo resolves to this). Week navigation keeps the selected weekday when shifting; today gets an accent border, selected day is the accent-filled active chip, past days dim, and days with entries show per-slot dots (capped at 4).
  - **Mobile layout: single column; the "Saved & Favorited" + search picker is a bottom sheet** (`lg:hidden` overlay) opened by "Add a Recipe" / "ADD <SLOT>" cells. The sheet covers the drop targets, so mobile is tap-first: tapping a picker row opened from an ADD cell assigns straight to that slot (POST), otherwise it opens the Quick Add modal pre-targeted at the selected day. Drag lives on `lg+` where the picker is a static third column.
  - **Drop targets**: slot sections (`{date, slot}`) accept both picker recipes (POST `/meal-plans`) and dish cards (PATCH reassign); week-strip day cells accept recipes by opening the Quick Add modal pre-targeted at that date (slot stays explicit — never guess) and dish cards by PATCHing just `date` (keeps the slot). One `DndContext` with `pointerWithin` + PointerSensor `distance: 4` (same activation as the block editor, so clicks pass through).
  - **QuickAddModal `plannerDate` prop**: slot rows pass it as `date` (schema already supported it), so previews read "adds to: Aug 31's Dinner" instead of next-occurrence resolution.
  - Empty-day state follows the `meal_planner_empty_state` mockup verbatim (big centered cell, circular plate icon, "Your day is looking a bit empty.", accent "Add a Recipe" button) minus the mockup's hard 2px shadow (no-shadows rule); empty slots are dashed `hatch` "ADD BREAKFAST" cells. `meal_slot: null` entries render in a trailing "Scheduled" group (custom-time entries show their clock time, upcoming pins show `#UPCOMING`).
- **Grocery list drag-to-recategorize (design.md §3.6)**: each item row drags via a grip-handle button (GripVertical), category cells are droppables (same `pointerWithin` + `distance: 4` idiom as the planner). The handle — not the row — carries the drag listeners with `touch-none`: touch input requires `touch-action: none` for dnd-kit's PointerSensor to see the gesture at all (without it the browser claims the touch for scrolling — this is why drag silently no-ops in devtools mobile emulation), but applying it to the whole row would make the list unscrollable since grocery drag is vertical. All eight categories always render — empty ones as compact dashed "drop items here" cells — so every category is a reachable drop target; a drop PATCHes `{ category }` and the API persists it to the Ingredient master row (survives regeneration, development.md §6 item 4). Dropping into the item's current category is a no-op. `DndContext` lives inside `CategoryGroups` (not the page component) so the mutation gets a non-null `list` without hook gymnastics. The planner's draggables still lack `touch-none` — deliberate (mobile planner is tap-first per the Phase 6 decision) but revisit with the same grip-handle pattern if touch drag is wanted there.
- **Phase 8 search screen (design.md §3.2, §2.4 #4, §4.6, §4.7)**: all filtering moved server-side — `search-client.tsx` queries `api.searchRecipes({ q, tags, ingredients })` (key `["recipes","search", q, tags, ingredientIds]`, 300ms-debounced q, `placeholderData` keeps the list steady while re-querying). The old All/Under-30m placeholder chips are gone: "Under 30 min" is now a prep_time tag reachable through the panel. **FilterTagPanel** (`components/filter-tag-panel.tsx`) is a right-side slide-out (overlay + `max-w-xs` sheet) with the "Select Filter Tags" title, Done/Clear-all footer, and expandable groups — system tags are flat, so roots group by `tag_type` into the "Active Item ⌄" sections; genuinely nested custom tags render as expandable parent rows with indented children (the §2.4 #4 one-level-nest). Selection lives in the parent and toggles live, so §4.6's "panel closes → chips update → re-query" holds by construction. **IngredientHavePicker** (`components/ingredient-have-picker.tsx`) is the §4.7 input mode — toggled by an "Ingredients I have" chip (Apple icon, count badge) — with debounced autocomplete (`GET /ingredients?q=`), Enter-picks-first, and removable picked-ingredient chips. Result cells show `matched/total main · N%` (mono, accent) plus a "Missing: …" line and the **"Buy N missing items to make this"** button, which appends the recipe to the active grocery list (`POST /grocery-lists` mode "append" — generation is recipe-based, so the whole recipe enters the list; the missing count is the informational hook per §9 step 4). Selection state is local to the Search screen (not URL-encoded) — revisit with query-param state if deep-linking filtered searches matters.
- **Phase 7 Cooking Mode** (`timer-store.ts`, `floating-timer-pill.tsx`, `use-shake-to-advance.ts`):
  - **Timer store refactored from React Context to Zustand** (checklist names it; zustand was already a dep). The floating pill, step chips, and tab badges subscribe from different subtrees, and the shake hook's auto-start calls the store OUTSIDE React (`useTimerStore.getState().start(...)`), which context can't do. One 1s `tick()` drives every instance — started lazily on first `start()` and registered on `globalThis` so dev HMR doesn't stack duplicate intervals. `tick` is exported for the node test suite (`apps/web/tests/timer-store.test.ts`, 9 tests — web's first tests; run via `pnpm --filter @cookbook/web test`, tsx devDep pinned to match apps/api).
  - Step chips use a per-step selector (`s.timers.find(t => t.stepId === block.id)`) so an unrelated timer ticking doesn't re-render every step block.
  - **Completion alert**: pulse + 3 WebAudio beeps + `navigator.vibrate` + a system `Notification` — the Notification only fires if permission was ALREADY granted elsewhere; the timer never prompts (an unprompted permission popup from a countdown would be hostile). Every browser-API branch is try/catch so the store completes cleanly headless.
  - **Shake-to-advance is opt-in, persisted in localStorage** (`cookbook:shakeToAdvance`, default off — accidental-trigger concern in design.md §3.3.3). Toggle is a Vibrate-icon button in the reader's read-mode action row, turmeric when armed; enabling runs iOS's `DeviceMotionEvent.requestPermission()` inside the click gesture (§7.4 requirement). Detection: per-event magnitude DELTA > 20 m/s² with a 1.6s cooldown (a shake is one sharp spike; ambient movement is smooth), ignored while `document.visibilityState !== "visible"`. Scoping: `shakeOn && !editable && !!recipeId` — edit mode and create mode never listen.
  - "Current step" is derived from scroll position at trigger time (last step at/above viewport midpoint) rather than tracked state — no sync bugs between scrolling and the advance pointer; a shake at the last step toasts instead of scrolling.
  - **Fonts moved to `next/font/local`** (Phase 1 leftover): the three vendored woff2s now load via `localFont` in layout.tsx with `--font-jakarta`/`--font-work-sans`/`--font-jetbrains` variables; globals.css tokens wrap them with quoted-name fallbacks and the hand-written `@font-face` blocks are gone. Production builds preload; dev serves from `/_next/static/media/`. The src path is `../../public/fonts/...` (layout lives two levels deep).
  - **Motion sensors are secure-context-gated** (post-Phase-7 phone finding): shake-to-advance showed "Motion access is blocked" on a phone over plain-http LAN access, with no permission prompt ever appearing. Root cause: browsers gate devicemotion to secure contexts (https:// or localhost) — over `http://<LAN-IP>:3000` the API is absent or auto-denied, so no prompt exists to show. `requestMotionPermission()` now returns `"ok" | "denied" | "unsupported"` and the toggle's toast distinguishes the cases ("needs a secure connection" vs "was denied"); when enabled on `!window.isSecureContext` the success toast warns that the browser may never fire motion events there (Android Chrome exposes the interface but silently drops events on http). To actually use shake on a phone: Chrome's `unsafely-treat-insecure-origin-as-secure` flag (dev-only) or serve over HTTPS (e.g. Tailscale Serve's real ts.net certs).
- **Phase 9 Diet Preferences screen (design.md §3.7)** — `apps/web/src/app/profile/diet-profile-form.tsx`: diet-type chips (from `DIET_TYPE_LABELS`), big-9 allergen chips (error-colored when active — they *exclude* recipes), free-text excluded-ingredients list with Enter-to-add, cuisine chips from `CUISINE_OPTIONS`, all shared schemas from `@cookbook/shared`. **Deviation from the phase-09 todo, recorded here:** "React Hook Form" was skipped in favor of controlled state + the shared Zod schema validating server-side — the form is chip arrays + one text input (no per-field validation complexity to delegate), and §0's offline bias says don't add a dep for that. Save = `PUT /users/me/diet-profile`; the API normalizes allergies onto `KNOWN_ALLERGENS`, so round-trips display canonical names ("lactose" saves as "milk"). An all-empty save deletes the profile row (empty = no profile).
- **Phase 9 Dashboard "Upcoming Recipe" fallback (development.md §10)** — when no upcoming pins exist, the cell shows the top `GET /recommendations/internal` result framed as "Suggested for you" (distinct mono label over the cover, first `reason` as the subtitle) so a recommendation never reads as a planned meal. The recommendations query is `enabled` only when the upcoming query resolves empty — it costs a second request on that path only. With neither pins nor recommendations, the old "Plan your first meal" empty state stands. Saving from the profile screen invalidates `["recommendations"]` so the fallback re-derives immediately.
- **Phase 9 cooked-history tracking** — `reader-client.tsx` fires `POST /recipes/:id/cooked` in an effect when the reader is opened scoped to a meal occasion (`?date=&slot=` or `?upcoming=1`) AND the occasion data has loaded; each dish opened via the tab strip counts (switching tabs = cooking that dish). Fire-and-forget with swallowed errors — the signal is best-effort, never user-visible. Plain `/recipes/:id` opens (browsing) deliberately record nothing.
- **Discover "Log manually" generates the full recipe (owner request, supersedes the plain-prefill flow)** — the card action is now a `useMutation` calling `POST /recommendations/discover/:id/expand`; the button spins ("Writing recipe…", the call takes ~15–25s on the free model). Success stashes the returned `RecipeBlocks` (lib/discover-draft.ts) and pushes `/recipes/new`; failure ALWAYS still navigates with the basic draft (`suggestionToBasicDraft`): quota → `flagLlmQuota()` + info toast, other errors → error toast. The stash mechanism is unchanged (localStorage, one-shot `takeDiscoverDraft` on the create page, keyed editor remount).
- **Discover cards are image-first (owner request, post-Phase 10)** — the card shows the dish photo (4:3, `object-cover`, top of the cell), the title, `why_recommended` clamped to one line, and the "Log manually" link. The summary is dropped from the card entirely (too much text per the owner); it survives in the API payload/DB and rides along when logging manually. `image_url` null (no TheMealDB match / download failed) renders a quiet `UtensilsCrossed` placeholder on `surface-container` — never a wrong-dish photo. **The `<img>` src MUST go through `apiAsset()`** (`/images/...` lives on the API origin — a raw path 404s against the web origin; first attempt shipped raw and images didn't render). Uses a plain `<img>` with the `no-img-element` rule disabled inline (local file, not a remote host; `next/image` gains nothing here).
- **Discover "Log manually" prefills the editor (owner request, supersedes the earlier no-param decision)** — ~~the link stashes the suggestion~~ *superseded by the generating flow above; the stash mechanism it introduced (localStorage, keyed remount) is what the full-recipe flow still uses.* localStorage over query params — a whole recipe doesn't belong in a URL, and params would force `useSearchParams` + a Suspense boundary (static-prerender bailout) onto the page.
- **Discover dashboard section is an accordion, collapsed by default (owner request, post-Phase 10)** — the section header (Sparkles + "Discover" + "Updated {date}" mono label) is a `button` with `aria-expanded` and a `ChevronDown` that rotates 180° on open; the body (quota notice, skeleton/empty/grid) renders only when open. The `["discover"]` query is gated with `enabled: open` — collapsed means not asked for, and the first-ever fetch can trigger the ~24h LLM refresh, so it waits for an explicit expand (§0 quota discipline) instead of firing on every dashboard load. The open/closed choice persists in localStorage (`discover-open`); fresh visitors default to collapsed.
- **Docker image (post-Phase 10, owner request)** — `apps/web/Dockerfile` (build context = repo root, `node:22-bookworm-slim`, multi-stage). `next.config.ts` now sets `output: "standalone"` — the runtime image copies `.next/standalone` + `.next/static` + `public/` and runs `node apps/web/server.js`. **`NEXT_PUBLIC_API_URL` is a Docker BUILD ARG** (Next inlines `NEXT_PUBLIC_*` at build time): empty default keeps api.ts's `${browser-hostname}:3001` fallback (plain LAN use); the Tailscale deploy rebuilds with `https://cookbook.<tailnet>.ts.net:8443`. Changing it requires a rebuild, not a restart. See docs/deploy.md.
