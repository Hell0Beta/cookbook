# AI-Pipeline Agent

## What you own

The intelligence layer: the Tagging Engine, the YouTube extraction pipeline, and both tiers of the recommendation engine. You implement these as importable services/modules that the backend hosts and calls — you own the logic, not the routes.

  - §5 YouTube Recipe Extraction (the full flow, the structured-extraction prompt, edge cases incl. quota-exceeded)
  - §6 Tagging Engine (all five responsibilities, rule-based-first approach, idempotency)

  - §3 Data Model — the fields you populate: `RecipeIngredient.role_tag`, `swap_suggestions`, `Recipe.diet_tags`, `Tag`/`RecipeTag`, `Ingredient.category`, `Recipe.source_type`

## Scope

**LLM client (development.md §0):** you own the single OpenRouter client module (`nvidia/nemotron-3.5-lightning:free`, key from server config/env). It must: normalize OpenRouter's rate/daily-limit errors into the `llm_quota_exceeded` condition, be usable from both sync request paths and the in-process queue, and never stream or poll. Budget discipline is yours: no LLM call where a rule-based path suffices, and batch ambiguous cases into one call where possible.

**Tagging Engine (`TaggingService`) — development.md §6.** Runs on every ingestion path (manual, public API, YouTube) before a recipe is saved:
1. Main vs Swap classification (`role_tag`): rule-based first pass (small quantities + known-flexible list → `swap`; proteins, primary starches, title-mentioned ingredients → `main`), LLM pass for ambiguous cases with 1-line rationale + 1–3 `swap_suggestions` per swappable ingredient.
2. Diet tag inference against allergen/animal-product dictionaries; flag ambiguous items (e.g. Worcestershire sauce) for LLM adjudication.
3. System Tag association: auto-populate `RecipeTag` for meal_type, cuisine, prep_time bucket (from summed step durations), difficulty (heuristic: step count + total time).
4. Grocery category tagging of `Ingredient.category` (seed from provider `aisle` where available, else lookup table, else LLM fallback).
5. Idempotency: re-runnable per changed row, not whole-recipe — avoid unnecessary LLM calls.

**YouTube extraction — development.md §5:**
- Extract `video_id`; fetch description (YouTube Data API `videos.list`) and transcript (youtube-transcript-style lib) as fallback/supplement.
- LLM structured extraction (OpenRouter, §0): description + transcript → strict JSON `{title, servings, ingredients: [{name, quantity, unit, raw_text}], steps: [{instruction, duration_minutes}]}`, nulls for missing values, durations inferred from timing cues.
- Hand results to the Tagging Engine, then return the populated block stack for user review — never auto-save silently.
- Edge cases: no captions → description only → sparse → error state prompting manual entry; non-English → extract/translate, flag `language`; **quota exhausted → `llm_quota_exceeded` so the UI shows the daily-limit alert and offers manual entry** (§5).
- Store the raw extraction result in the database (no Redis per §0) so re-imports/edits don't re-hit the API or the LLM.

**Recommendations — development.md §10:**
- Tier 1 (deterministic): filter library by `DietProfile` (diet_types, allergies, excluded_ingredients, preferred_cuisines); rank by recency of similar cooked recipes, pantry ingredient overlap, cuisine match. Powers Dashboard's "Upcoming Recipe".
- Tier 2 (LLM-generated "Discover"): job sends `DietProfile` + recent-cooked summary; the model generates ideas from its own knowledge (no web search on this model) → `{title, summary, why_recommended}` — **no `source_url`** (don't trust a small model to cite real URLs), short summaries only, never reproduced copyrighted recipe text. Persist in the DB with ~24h refresh cadence; skip entirely when the daily quota is exhausted (serve stale/empty results with a quota flag rather than erroring).

**Voice assistant intelligence — development.md §14 (phase 11):**
- `routeCookingIntent(text, context)` — the intent router as a pure function in `packages/shared` (§14.2): step control, ingredient lookup, timer control resolved without the LLM; everything else falls through to the LLM turn. Fail-soft — the router saves quota, it never gatekeeps.
- Chat-completion prompt assembly (§14.3) hosted in a service the backend's `/chat` routes call: context = recipe title + servings, current step ± neighbors, ingredients at current scale, timer summary, last ~8 persisted session turns. Short replies (≤ 2 sentences, `maxTokens` ≈ 200), `reasoning` off. Reuses the existing OpenRouter client — plain completion, no streaming (§0).

## Explicitly NOT your job

- **REST routes / queue infrastructure** — backend owns `/recipes/import/youtube`, `/recommendations/*`, and the in-process queue wiring. You own the modules they call.
- **Ingredient string parsing** ("2 cups flour, chopped" → `{quantity, unit, ingredient}`) and **unit conversion math** — integrations owns `parse-ingredient` normalization and the conversion tables. You consume their parsed output.
- **Public API import pipeline** (TheMealDB/Spoonacular fetch + field mapping) — integrations owns §4; your Tagging Engine is step 4 of that pipeline.
- **Any UI.** The frontend renders extraction loading states and review flows.
- **Prisma schema changes** — request them via the backend agent or propose a doc update.

## Key implementation notes (from development.md)

- Tagging is called **synchronously for small edits, via the in-process job queue for bulk/import** (§6 implementation note) — design the service API so both call patterns work.
- All ingestion paths converge on the Tagging Engine so every recipe has consistent system tags regardless of source (§6 intro).
- YouTube extraction step: providers rarely give per-step durations — estimate from instruction text ("simmer for 10 minutes" → 10) (§4 step 2).
- Tier 2 must be a separate "Discover" surface, never mixed into core dashboard results (§10).
- The LLM is **budgeted** (§0): the rule-based tagging pass must run standalone when the quota is exhausted — the LLM pass is an enhancement, never a hard dependency. Use structured extraction prompts that return only JSON, and validate/repair the model's JSON output defensively (small free-tier models malformed-output more often than Claude-class models).

## Definition of done

- [ ] Tagging engine handles all three ingestion paths and is idempotent (re-tag only changed rows).
- [ ] Rule-based pass runs before any LLM call and works standalone with the LLM disabled; LLM is reserved for ambiguous cases (quota discipline).
- [ ] LLM client normalizes OpenRouter daily-limit errors to `llm_quota_exceeded`; no AI feature throws an unhandled error at quota.
- [ ] YouTube extraction returns schema-valid JSON with nulls (never guessed values) and durations inferred from cues where possible; malformed LLM output is repaired or rejected, never silently trusted.
- [ ] Tier 1 has zero LLM cost; Tier 2 persisted with ~24h cadence, no `source_url`, no reproduced recipe text, skipped at quota.
- [ ] Services are pure modules importable by `apps/api` — no HTTP/route concerns inside them.
- [ ] Modules pass their own tests (unit tests for rule-based tagging and scoring); todo items checked off in `docs/todos/`.

## Decisions

*(record resolved open questions — e.g. exact prompt templates, flexible-ingredient seed list, difficulty heuristic constants)*
- **Tagging Engine v1 is pure rules, hosted as `apps/api/src/services/tagging.ts` + `packages/shared/src/tagging.ts` (Phase 3)**: shared holds the dictionaries/heuristics (testable standalone, no I/O); the api service persists (`tagRecipe(recipeId)` recomputes role_tag per RecipeIngredient, Recipe.dietTags + difficulty, and syncs system Tag/RecipeTag rows — only rows that actually changed get written, §6.5). It runs on EVERY save path (POST /recipes, PUT /:id/blocks, import) since §6 says all ingestion paths pass through it. The LLM pass for ambiguous cases is NOT wired yet — `services/openrouter.ts` exists (quota → `ApiError(429, "llm_quota_exceeded")`, `llmJson` strips markdown fences) and is the only sanctioned way to call the model; nothing calls it until the §6.1 enhancement or Phase 4 YouTube extraction lands.
- **`normalizeIngredientName` semantics (shared/tagging.ts)**: lowercase, strip parens + punctuation (hyphens split so "free-range" hits the "free range" descriptor), drop descriptor PHRASES anywhere in the name (longest-first: "plus extra" beats "extra"), drop unit words ("2 cups flour" → "flour"), singularize ("tomatoes" → "tomato", "ies" → "y"). This is the one canonicalizer for Ingredient-master matching, diet dictionaries, and category lookup — raw text like "500g chicken breast" classifies correctly without pre-parsing.
- **Difficulty heuristic constants (§6.3 open question)**: score = stepCount + totalMinutes/15 (untimed recipes score as 30 min); ≤8 easy, ≤15 medium, else hard. Arrabiata (3 steps, ~14 min) lands easy; a 15-step 90-minute braise lands hard. Adjust the thresholds only with new test cases in `packages/shared/tests/tagging.test.js`.
- **TaggingService runs synchronously in-request for imports too (Phase 3)** — the in-process queue isn't wired yet (no queue exists); the todo's "via the job queue" clause is satisfied structurally (it's a plain async function the future queue can call). Revisit when Phase 4's YouTube import needs background work.
- **YouTube extraction (Phase 4, development.md §5)**: `apps/api/src/services/youtube.ts` — `extractVideoId` (pure, in `packages/shared/src/youtube.ts`, unit-tested) recognizes watch/youtu.be/shorts/embed/live/bare-id forms. Description+title come from a **keyless watch-page scrape** (`ytInitialPlayerResponse` via brace-matched JSON extraction — the script body has trailing statements, so slice-to-`</script>` breaks), with oEmbed as title fallback; the Data API path from §2/§5 is NOT used because no owner key exists (same pattern as Spoonacular: if one is ever provided, add it behind a config flag). Transcript via the spec-named `youtube-transcript` lib; caption fetch failures degrade to description-only. Content budget: 6000 chars description + 14000 chars transcript. Sparse rule: description < 80 chars AND no transcript → 422 `no_recipe_content`.
- **nemotron needs reasoning disabled (Phase 4)**: the free model dumps chain-of-thought into `content` and truncates before the answer (`finish_reason: "length"`). Every OpenRouter call now sends `reasoning: { effort: "none", exclude: true }` in `openrouter.ts` — without it NO llmJson call can succeed. `llmJson` additionally repairs trailing junk by brace-extracting the first balanced JSON object before rejecting (§5 step 4's "repair or reject").
- **Extraction contract (Phase 4)**: prompt lives in `extractionPrompt()`; output validated by `LlmRecipeExtraction` (shared/youtube.ts — permissive `.catch()` at field level so one weird ingredient degrades alone, never the whole import); zero ingredients AND zero steps → 422 `no_recipe_content`. LLM units mapped to the `Unit` enum via a word table, unmapped → null. Draft ingredients get `role_tag` from the rule-based `classifyRoleTag` (the §6.1 LLM ambiguity pass is still unwired); diet/system tags apply at save time via `tagRecipe` since drafts aren't recipes yet. Non-English: prompt instructs extraction into English + reporting `language`; language also falls back to the transcript's lang. Thumbnails (`i.ytimg.com/vi/<id>/hqdefault.jpg`) download server-side into the local image store (§0: no runtime ytimg requests from the browser).
- **Match-score formula resolved (Phase 8, development.md §9 step 3)**: `swap`-tagged ingredients are **excluded from the denominator entirely** (§9's primary option; the ~0.3 weighting was the alternative) — they neither help nor hurt the score and never surface as missing, since the user can substitute them. `scoreIngredientMatch` lives in `packages/shared/src/search.ts` as a pure function (tested in tests/search.test.js), consumed by the backend's `GET /recipes?ingredients=` — the backend never reimplements it. A row matches when its master `ingredient_id` is in the pantry OR its normalized name is (name matching exists so manual recipes, which link no master rows, stay searchable). Recipes with zero main ingredients score 0 and are filtered out of ingredient-mode results (≥1 matched main required).
- **Tier 2 "Discover" refresh is on-demand, not scheduled (Phase 10)**: `apps/api/src/services/discover.ts` — the first `GET /recommendations/discover` after the newest `DiscoverSuggestion.generatedAt` is older than `DISCOVER_REFRESH_MS` (24h) runs the refresh inline (awaited, so the caller sees fresh rows; ~26s live on the free tier — the UI's hatch skeleton covers it). No scheduler/cron: a user who never opens the dashboard costs zero quota, which is the right trade on a free daily budget. Concurrent callers share one in-flight promise via a module-level per-user Map — one LLM call per refresh, `maxTokens: 1024`, temperature 0 (`llmJson` default). Signals: last 30 `CookedEvent`s + 20 recent saved-recipe titles, both deduped, titles only.
- **Discover prompt + repair are pure, in shared (Phase 10)**: `buildDiscoverMessages` / `sanitizeDiscoverOutput` in `packages/shared/src/recommendations.ts` (tested in tests/recommendations.test.js, which also hosts the Tier-1 tests). The sanitizer drops junk entries, clips to the schema maxes (120/400/300), dedupes titles case-insensitively, caps at `DISCOVER_MAX_SUGGESTIONS` (6), accepts the `whyRecommended` camelCase alias small models emit, strips unsanctioned keys (a hallucinated `source_url` never persists), and returns **null** when nothing usable remains — the service then keeps the stale rows rather than overwriting them with garbage (repair-or-reject, same stance as §5 step 4).
- **Discover never errors for LLM reasons (Phase 10, §10)**: `runRefresh` never rejects — `429 llm_quota_exceeded` → serve stale/empty rows with `quota_exhausted: true`; any other LLM failure (502/503, key unconfigured) → stale/empty rows with `quota_exhausted: false`. The route always answers 200 with whatever is persisted; only non-LLM (DB) failures reach the error handler.
- **Discover UI (Phase 10)**: `DiscoverSection` (no props) in `apps/web/src/components/discover-section.tsx`, query key `["discover"]`, `staleTime` 5 min (quota-consuming — never refetch on focus; providers.tsx already disables that globally). `quota_exhausted: true` renders the design.md §5 notice inline in the section AND calls `flagLlmQuota()` so the app-wide banner other AI entry points listen to also raises. "Log manually" is a plain link to `/recipes/new` — the create page reads no params, and a title prefill would need `useSearchParams` + a Suspense boundary (forces dynamic rendering); not clean, so no param is passed. **Mounting is the frontend agent's one-liner**: render `<DiscoverSection />` in `apps/web/src/app/page.tsx` below `<DashboardGrid />` (the last unchecked phase-10 UI item).
- **Discover smoke (2026-08-31)**: live first call returned 6 valid persisted suggestions in ~26s (`quota_exhausted: false`, `refreshed_at` set); immediate second call served the rows in 12ms (cadence check, no second LLM call). The quota-exhausted branch is trusted against `llmJson`'s documented `ApiError(429, "llm_quota_exceeded")` contract (same mechanism the YouTube import path exercises in production).
- **Discover "Log manually" expands to a full recipe (owner request, post-Phase 10)** — clicking the card's action now makes one user-initiated LLM call (`POST /recommendations/discover/:id/expand` → `services/discover-recipe.ts`) that turns the suggestion into a complete `RecipeBlocks` draft: `buildDiscoverRecipeMessages` (shared, tested) reuses the §5 extraction JSON contract (`{servings, ingredients[{name,quantity,unit,raw_text}], steps[{instruction,duration_minutes}]}`), so the api maps it through `extractionToBlocks` — extracted from youtube.ts so both imports build blocks identically (role tags, duration estimation, unit mapping). The suggestion's own title/summary/image override the LLM's; `source_type: "manual"`. Diet safety is re-asserted in the prompt (allergies/exclusions re-sent). Unlike the refresh this call DOES 429 on quota — user-initiated like YouTube import; the frontend falls back to the basic title/summary/photo draft. Live smoke 2026-08-31: 12 ingredients with quantities/units/role tags + 6 timed steps in ~14.5s.
- **llmJson repair chain hardened (post-Phase 10)** — the free model's JSON malformations vary run to run; diagnosed live by capturing raw responses. Observed shapes: unquoted keys (`,summary:"…"`), **half-quoted keys** (`,summary":` — closing quote only), `=` instead of `:` separators, trailing commas, stray closers/trailing junk after the final `}`, and **missing brackets** (a suggestion object that never closes before `]`). `openrouter.ts` now escalates through parse-validated candidates: as-is → extract-first-balanced-object → JS-literal key repair (optional quotes + `=`/`:` separator) → stack-based bracket repair (insert missing closers on mismatch, auto-close at end, drop stray closers). Every candidate is re-validated by `JSON.parse`, so a botched repair is rejected, never applied; unparseable responses log their first 200 chars so the next malformation shape is diagnosable. Also: Discover's `maxTokens` went 1024 → 2048 — truncation produces unbalanced JSON that no repair can fix, and the search_term field pushed output past 1024 (verified live).
- **Discover hero images resolved at refresh time (post-Phase 10, owner request)** — cards are image-first now, so each refresh asks the LLM for one extra structured field, `search_term` (the dish's main ingredient, 1–2 words; sanitized/kept in `sanitizeDiscoverOutput`, never surfaced to the client). `discover.ts` then runs `findMealDbThumb(search_term, title)` per suggestion — TheMealDB `filter.php?i=` (24h TTL cache) plus word-overlap title matching, zero-overlap → null (a wrong-dish photo is worse than none) — and downloads the winner via `saveImageFromUrl` into DATA_DIR/images, storing the local `/images/...` path as `DiscoverSuggestion.image_url`. Every failure degrades to an image-less card; nothing in this path can fail the refresh. This is a §0 amendment recorded in development.md §0/§10: TheMealDB lookups are now sanctioned for Discover image resolution (≤6 batched calls per user per day) in addition to user-initiated imports.
- **Tier 1 ranking is a pure shared function (Phase 9, development.md §10)**: `rankInternalRecommendations` in `packages/shared/src/recommendations.ts` (tested in tests/recommendations.test.js — 11 Tier-1 tests incl. the allergen-alias and peanut-butter-guard cases). Filtering: excluded ingredients by substring on raw lines; allergies by matching normalized ingredient names against the allergen's FULL synonym list ("heavy cream" must trip a milk allergy — matching only the canonical string was a real bug the tests caught), with a guard so non-dairy compounds ("peanut butter") don't false-positive on the "butter" synonym; vegan/vegetarian/gluten_free/dairy_free filter on the Tagging Engine's positive `diet_tags` (consistent by construction — the same dictionaries decide both). **keto/paleo deliberately don't filter** — `inferDietTags` can't establish them, so filtering would nuke the library; recorded as a known limit. **Pantry overlap signal deferred**: no pantry concept exists yet (§3 has no Pantry entity; the "Ingredients I have" picker is per-search, unpersisted), so ranking = preferred-cuisine match (+3) + time-decayed Jaccard similarity to 30-day cooked recipes + new-in-cookbook bonus (+0.5, 14 days) − just-cooked penalty (−2, 3 days); revisit when a pantry lands. Reasons strings ride along so the dashboard fallback can explain itself.
- **Discover switched from LLM generation to local-dataset selection (owner request, 2026-09-01, supersedes the LLM-refresh and expansion decisions above)** — `services/discover.ts` no longer calls OpenRouter at all. The ~24h refresh now selects 6 recipes from the imported dataset (`source_type = "dataset"`): hard-filter by allergies/excluded ingredients (ingredient raw-text substring), soft-score cuisine + diet-tag match, deterministic seeded shuffle (xorshift32, seed = hash(day + userId)) for daily rotation. `DiscoverSuggestion.recipeId` (schema addition, §3 updated) points the card at the full recipe — `POST /discover/:id/expand`, `services/discover-recipe.ts`, `buildDiscoverMessages`/`buildDiscoverRecipeMessages`/`sanitizeDiscoverOutput` (and their tests) are REMOVED. `findMealDbThumb` in mealdb.ts is now unused by Discover (still fine to delete if nothing else picks it up). Why-recommended copy is rule-derived (cuisine/diet/fallback) — with the LLM gone the copy must be derivable from data we have.
- **Phase 11 voice assistant (development.md §14)**: prompt assembly is the pure `buildCookingChatMessages` in `packages/shared/src/chat.ts` (tested in tests/chat.test.js — current-step windowing, history trimming, timer formatting). Persona: ≤2 spoken sentences, no markdown; context = title + servings, current step ± neighbors ONLY (budget), full ingredient list at the client's current scale (lines pair raw text with the scaled value, same shape as GET /recipes/:id/scale), timer summary, last 8 exchanges (`quota_notice` filtered). The service call is `services/chat.ts` → `llmComplete` (plain text — NOT llmJson; no JSON to repair) with `maxTokens: 220`, `temperature: 0.4`, reasoning-off inherited from the client. The intent router is `routeCookingIntent` in `packages/shared/src/chat-router.ts`: regex-based step/timer/ingredient intents with a 5-word gate on bare commands ("what should I make next time?" must fall through), time-left patterns constrained to explicit remaining-time queries ("how long do I cook the pasta" is a general question), and word-overlap ingredient matching that prefers recall — a miss costs one LLM turn, a false positive executes a wrong action.
