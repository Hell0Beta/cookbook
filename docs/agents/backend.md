# Backend Agent

## What you own

Everything in `apps/api/` — the REST API, database schema, auth, job queue wiring, and the persistence/read side of every feature. You are the host for the domain services other agents build (tagging, extraction, import, recommendations): you own the routes and call their modules.

## Explicit read list

- `docs/development.md` — **your primary document.**
  - §0 Deployment Constraints — **binding: SQLite, no Redis/S3/OAuth, in-process queue, offline-first, ≤5 users.**
  - §1 Suggested Stack (NestJS/Express, SQLite via Prisma, in-process queue, OpenRouter LLM, local file storage, username-only auth)
  - §2 Recommended Libraries (Prisma, Zod, p-queue context)
  - §3 Data Model — **every entity and field name is contractual.** `MealPlanEntry.is_upcoming_pin`, `RecipeIngredient.role_tag`, `source_type` enum, `MealPlanEntry.scheduled_at` nullability, multi-dish semantics (no "Meal" grouping entity).
  - §7 "Quick Add to Meal (Modal)" — the three quick-add modes and slot resolution logic
  - §8 "Serving Scaling & Grocery List Aggregation" — persistence side (`GroceryList`/`GroceryListItem` rows, `source_recipe_ids` traceability)
  - §14 "Voice Cooking Assistant" — the `/chat/*` routes you own (session resolve/resume, LLM message turn, client-resolved-turn logging) and the `CookingSession`/`ChatMessage` entities
  - §11 API Surface — the full REST contract (representative; adjust names only if you update this doc)
  - §12 Build Phases — sequencing
- `docs/design.md` — skim §3.4 (Quick Add modal behavior), §3.5 (what the planner's three panels each query), §4.1 (multi-recipe occurrence semantics). You need enough UI context to shape the endpoints, not to build UI.
- Your phase checklists in `docs/todos/`.

## Scope

- Prisma schema (SQLite connector) for every entity in development.md §3, plus migrations. Field names identical to the doc.
- Zod request/response schemas — defined in `packages/shared` where the frontend needs them too; API-only shapes can live in `apps/api`.
- Auth: **username-only** signup/login + long-lived signed session cookie (development.md §0 — identification, not a security boundary). Per-user scoping on every resource.
- **LLM quota handling:** detect OpenRouter's daily-limit response, return `429 { "error": "llm_quota_exceeded" }` (or `quota_exhausted: true` for stale-OK reads like Discover) per §11's error convention. Every route that triggers an LLM call must handle this path.
- Every route in §11, notably:
  - `POST /meal-plans/quick-add` — the three modes: `now` → `is_upcoming_pin = true, date = today`; `slot` → next occurrence of that slot (today if not passed, else tomorrow), **exposed as a pure exported function in `packages/shared`** so the frontend can preview; `custom_minutes` → `scheduled_at = now + minutes`, `meal_slot = null`.
  - `GET /meal-plans/upcoming` — resolves the Dashboard's "Upcoming Recipe" occurrence; may return >1 recipe (query the `is_upcoming_pin` flag, don't infer from date/time).
  - `GET /meal-plans/for-slot?date=&slot=` — all recipes for a meal occurrence → drives the Reader's multi-recipe tabs.
  - `GET /tags` — nested filter tag tree from `Tag.parent_tag_id`.
  - `PUT /recipes/:id/blocks` — single batch update of the client-side block array (§7.1).
- Job queue: **in-process** (`p-queue` or a plain promise-queue module — no Redis/BullMQ per §0) for async work: YouTube extraction, AI tagging on bulk/import, recommendation refresh. You own the queue infrastructure; the job payloads' logic belongs to the owning agent. Persist job state to SQLite if durability is needed.
- **Image storage: local data directory** (e.g. `/data/images` or a configurable path) served through a static route — no S3.
- In-process LRU/Map cache with TTL for external API responses (§0) — no Redis.
- **Voice assistant routes (§14, phase 11):** `POST /chat/sessions` (resume-today-or-create by occasion), `GET /chat/sessions/:id`, `POST /chat/sessions/:id/messages` (persist user message → ai-pipeline's chat completion → persist reply; **429 `llm_quota_exceeded` only after the user message is persisted**), `POST /chat/sessions/:id/log` (fire-and-forget persistence of client-resolved turns — never triggers an LLM call). Plus the `CookingSession`/`ChatMessage` Prisma entities, field names per §3.

## Explicitly NOT your job

- **The tagging engine's classification logic** (rule-based + LLM passes) — ai-pipeline owns `TaggingService` as a module; you call it synchronously for small edits and enqueue it for imports (§6 implementation note).
- **YouTube extraction logic** (transcript fetch, LLM structured extraction via OpenRouter) — ai-pipeline owns it; you own the `POST /recipes/import/youtube` route, job scheduling, and persistence of the raw extraction result.
- **Recommendation ranking** (Tier 1 filter/rank, Tier 2 LLM "Discover" job) — ai-pipeline owns; you own the `/recommendations/*` routes.
- **Public API normalization, ingredient parsing, unit conversion math** — integrations owns these as modules; you own the `/recipes/import/public-api` route and the grocery aggregation *orchestration* (calling the conversion engine, persisting results).
- **Any UI.** Frontend agent owns `apps/web/`.
- Changing the data model unilaterally — field names are contractual; a rename requires updating `docs/development.md` §3 in the same change.

## Key implementation notes (from development.md)

- **§0 is binding:** SQLite, no external services, ≤5 concurrent users — size choices accordingly (no connection-pool tuning, no cache tiers, keep memory footprint modest for 8 GB RAM shared with the OS).
- Multiple dishes per meal: a single `(date, meal_slot)` — or a single `scheduled_at` occasion — can have multiple `MealPlanEntry` rows. No grouping entity; readers query by occasion and render tabs (§3, MealPlanEntry).
- `total_time_minutes` is derived: sum of step durations + prep buffer (§3, Recipe).
- `RecipeIngredient.ingredient_id` is nullable (unmatched free-text) and `quantity` is nullable ("to taste" never scales) (§3).
- Imported recipes must run through the Tagging Engine before saving — never trust provider tags as sole truth (§4 step 4).
- Grocery list items carry `source_recipe_ids` arrays for traceability (§3, GroceryListItem).

## Decisions

*(record resolved open questions — e.g. NestJS vs Express, and any §11 route adjustments — here; update development.md §11 in the same change if routes change)*

- **Express (not NestJS)** — the app is small (≤5 users, in-process queue); NestJS's DI/module machinery is dead weight on an 8 GB homeserver box. Phase 1 routes live in `apps/api/src/routes/`, shared error convention in `middleware/error.ts`.
- **All runtime data under `apps/api/data/`** — SQLite file + uploaded images both live there (one directory to back up, per §0). Gotcha: Prisma resolves relative SQLite paths against `prisma/schema.prisma`, so `DATABASE_URL` is `file:../data/cookbook.db`, while `DATA_DIR=./data` is resolved from cwd. Don't "fix" the apparent inconsistency.
- **Recipe↔GroceryList has no FK relation** — traceability goes through `GroceryListItem.sourceRecipeIds` (JSON array of recipe ids), so a recipe deletion doesn't cascade-wipe grocery rows. `Recipe.groceryListItems` back-relation was removed from the Prisma schema for this reason.
- **`total_time_minutes` is derived on write** — `serializeRecipe` recomputes it as Σ step durations + 10-min prep buffer; client-sent values are ignored. Phase 2+ can make the buffer configurable.
- **Root `pnpm dev` builds `@cookbook/shared` first** — apps import `@cookbook/shared/dist`, so the root dev script chains `pnpm --filter @cookbook/shared build` before starting web+api. If you add a new export to shared while `pnpm dev` is running, rerun the shared build (or restart dev) — tsx watch does not watch it.
- **Grocery lists (Phase 2):** one *active* list per user — `POST /grocery-lists` archives the previous active list in the same transaction, and `GET /grocery-lists/active` (an addition beyond §11's listed routes, needed by the Dashboard cell + screen) returns it or 404. Added `GroceryListItem.label` (nullable display-name snapshot) for unmatched free-text items and manual adds — development.md §3 updated in the same change. Aggregation math is integrations-owned in `@cookbook/shared/grocery.ts`; the route only scales exactly (`quantity × target/base`, no rounding) and persists.
- **CORS `WEB_ORIGIN` accepts a comma-separated list** — `config.webOrigins` (array) replaces the single `config.webOrigin`, so phone/LAN testing can allow `http://localhost:3000,http://<lan-ip>:3000` simultaneously. The web client derives its API base URL from `window.location.hostname` (`apps/web/src/lib/api.ts`), so no `.env.local` is needed for LAN testing — don't set `NEXT_PUBLIC_API_URL` in dev, it desyncs the cookie host (cookies are host-scoped: a LAN-IP API URL logs out localhost users with a 401). Root has `pnpm qr` (dev-only `qrcode-terminal` dep) to print scannable QR codes for the LAN URLs.
- **`POST /grocery-lists` append mode (bugfix round post-Phase 2):** `CreateGroceryListInput.mode: "replace" | "append"` (default replace). The Reader's "Add to grocery list" appends per design.md §3.6 — it must merge into the active list, not wipe it. Implementation: in append mode the existing active list's items are converted back into `GroceryEntry`s and fed through the same `aggregateGroceryList` — one entry per source recipe per item (`sourceRecipeIds`, or the item's own id for manual adds) with an even per-source quantity share, so re-aggregation reproduces the original quantities. Purchased state survives the rewrite: items are keyed `${ingredientId ?? name:label}|${unit}` before the transaction and `is_purchased` is re-applied to merged rows of the same identity+unit. Append with no active list falls through to create. development.md §8.2/§11 updated in the same change.
- **Empty draft blocks are dropped on save (bugfix round post-Phase 2):** `writeBlocks` skips ingredient/step/note blocks whose text is empty/whitespace, and the shared schemas allow `step_number: 0` and empty text strings — the client inserts transient empty blocks ("+" inserter, mid-draft saves) that previously failed Zod validation with a 400 (misread by the user as a 404). The step renumbering in the same write path keeps `step_number` contiguous afterwards, and the client re-syncs its state from the save response.
- **Phase 3 routes (development.md §4/§11)**: `POST /recipes/import/public-api` (+ `GET /recipes/import/public-api/search?q=`) mounted at `/recipes/import` BEFORE `/recipes` so the literal path can't be captured by `/:id`. Imports persist shared recipes (`userId: null`); `GET /recipes` therefore lists `userId = me OR null`. `GET /tags` returns the nested tree (system tags userId-null + caller's customs); `POST /tags` rejects dupes on (label, tag_type) across system+user scope with 409 `tag_exists`. `tagRecipe` is invoked after every recipe write (create, block update, import) — all §6 ingestion paths run through it.
- **OpenRouter quota errors normalize at the client (services/openrouter.ts)**: HTTP 429 OR a quota-marker string in the error body (rate limit/quota/free tier/…) → `ApiError(429, "llm_quota_exceeded")`, which the error middleware already serializes per §11's convention. Missing API key → 503 `llm_unavailable` (AI features off, core flows unaffected). Nothing calls the LLM yet in Phase 3 — the wiring exists for §6.1's ambiguity pass and Phase 4.
- **Recipe persistence extracted to `src/recipes/persist.ts`** (`writeBlocks`, `createRecipeFromBlocks`, `metaOf`, `stepDurationsOf`, `recipeInclude`): routes and the import pipeline share one write path, so block-row semantics can't drift between manual saves and imports.
- **Phase 5 meal-plans routes (development.md §7.2/§11)**: `mealPlansRouter` (routes/meal-plans.ts) mounted at `/meal-plans` — `POST /quick-add`, `GET /upcoming`, `GET /for-slot?date=&slot=`, `GET /?date=|?week=`, and `POST /` (direct date/slot assignment, the Phase 6 drag-drop target). Quick-add resolution is NOT in the route: `resolveQuickAddTarget(mode, opts, now)` lives in `@cookbook/shared/meal-plan.ts` (pure, unit-tested in packages/shared/tests/meal-plan.test.js) and the route calls it with server time — the modal previews with client time, so "adds to: Today's Dinner" is the same computation. `mode: "slot"` accepts an optional explicit `date` override (used by no caller yet; quick-add always resolves next occurrence) — decided since the todo's request shape includes `date?`. `servings_planned` defaults to the recipe's `baseServings` on every entry-creation path. `GET /upcoming` queries the `is_upcoming_pin` flag directly (never infers from date/time, §3) and returns multiple pins newest-first — the reader dedupes by `recipe_id`. `?week=` resolves to Monday..Sunday (local time) of the week containing the given date. MealPlanEntry's model + table already existed (pre-provisioned in Phase 1 schema); only the Prisma client regeneration was needed.
- **`POST /recipes/import/youtube` is synchronous and returns a DRAFT (Phase 4, development.md §5/§11)**: consistent with the Phase 3 sync-not-queue decision — one scrape + one transcript fetch + one LLM call completes in seconds-to-a-minute, covered by the frontend loading state. It creates NO recipe: the response is `{ video_id, language, existing_recipe_id, blocks }` and the user saves through the normal `POST /recipes` (§5 step 5 — never auto-save). Idempotency: a URL already saved (`sourceType: "youtube_import"` + canonical watch URL) returns `existing_recipe_id` with `blocks: null`; repeat extractions within 24h are served from an in-process `ttlCache` — §5 step 6 explicitly allows "database or in-process cache" instead of a Prisma table (this also avoided a migration conflict with Phase 5's concurrent work). Quota exhaustion flows through the openrouter client as 429 `llm_quota_exceeded`.
- **API now loads `apps/api/.env` itself (Phase 4)**: `process.loadEnvFile()` at the top of `config.ts` (Node ≥20.6 built-in, no dotenv dep). Prisma loads only `DATABASE_URL` from .env — `OPENROUTER_API_KEY` was previously invisible to the app (Phase 3 never called the LLM, so nobody noticed). The key now lives in `apps/api/.env` alongside the root `.env`. Gotcha: tsx watch does NOT re-read .env on reload — restart the dev server after changing it.
- **Phase 6: Favorite model + meal-plan PATCH/DELETE (development.md §3/§11)**: `Favorite` (unique `(userId, recipeId)`, cascades) powers `GET /recipes/favorites` — registered BEFORE `/:id` in recipes.ts (same ordering rule as `/recipes/import`) so "favorites" can't be parsed as an id; it selects the same summary shape as `GET /recipes`. `POST /:id/favorite` is an idempotent upsert (201 `{id, favorited: true}`), `DELETE` is a `deleteMany` no-op-204. `PATCH /meal-plans/:id` uses the shared `MealPlanEntryUpdate` schema; supplying `date` or `meal_slot` is an explicit placement and clears `is_upcoming_pin` + `scheduled_at` (an entry dragged onto the calendar stops being an "upcoming" pin — patching only `servings_planned` leaves occasion fields alone). `DELETE /meal-plans/:id` → 204. Both load via `getOwnEntry` (404 for missing AND other users' rows alike). Dev DB schema changes apply with `pnpm db:push` — the dev database was initialized with `db push`, so `prisma migrate dev` wants a destructive reset; don't run it against `data/cookbook.db` (note: `prisma generate` can hit EPERM renaming the Windows query-engine DLL while the dev server is running — restart the server to release the lock).
- **Phase 8 search routes (development.md §9, §11)**: `GET /recipes` grew `?tags=&q=&ingredients=` (all optional, comma-separated ids). **Tags combine with AND** (`tags: { some: { tagId } }` per selected tag — "Dinner" + "Vegetarian" narrows, per filter-panel intent); `q` is a title substring match done in-memory after the Prisma fetch (SQLite `contains` is ASCII-case-insensitive via LIKE, but in-memory keeps one code path for the scoring branch). `ingredients` takes master Ingredient **ids** (what autocomplete returns); the route resolves them to canonical names so the shared scorer can also name-match manual recipes, whose `RecipeIngredient` rows link no master row. With `ingredients` present, results carry `match_score` / `matched_main` / `total_main` / `missing_ingredients` and only recipes with ≥1 matched main are returned (a 0-match long tail is noise), ranked score desc → missing count asc → title. New router `GET /ingredients?q=` (mounted at `/ingredients`, autocomplete against the Ingredient master, prefix-first ranking, top 20) is an addition beyond §11's representative list. The inverted index itself lives in `services/ingredient-index.ts` (see integrations decisions); it's invalidated from `persist.writeBlocks` (covers manual saves AND imports — the one shared write path) plus the `DELETE /recipes/:id` route, and rebuilds lazily on next search. No schema change, no new table, no daemon (§0).
- **Discover expansion route (post-Phase 10, owner request)**: `POST /recommendations/discover/:id/expand` (routes/recommendations.ts) delegates to `services/discover-recipe.ts` (ai-pipeline's logic) and returns a `RecipeBlocks` draft — nothing persists until the user saves from the editor. Scoped `findFirst({ id, userId })` → 404 for other users' suggestions. Quota exhaustion propagates as `429 llm_quota_exceeded` (user-initiated call, same as YouTube import) — deliberately unlike `GET /discover`, which never errors.
- **CORS allows any private-network origin (post-Phase 10, owner bug report)** — phone login/signup failed because the phone reached the app via the LAN IP while `WEB_ORIGIN` only listed localhost (+ a Tailscale IP): the browser blocked every credentialed response. `config.ts` now exports `corsOriginAllowed(origin, webOrigins)`: the explicit `WEB_ORIGIN` allowlist PLUS any http(s) origin on localhost or a private IPv4 range (10/8, 127/8, 172.16/12, 192.168/16, 169.254 link-local, 100.64/10 CGNAT/Tailscale). Rationale: §0 is a username-only-auth, single-trusted-home-network deployment, phones connect by whichever interface is handy, and DHCP renumbers — a static list breaks on every network change. Public origins still get no ACAO header (verified live). `server.ts` passes it as a cors `origin` function; requests without an Origin header (curl, same-origin) pass through.
- **Phase 9 diet-profile + cooked-event + recommendations routes (development.md §3/§10/§11)**: `PUT /users/me/diet-profile` (routes/users.ts) upserts the row, normalizing `allergies` through `normalizeAllergenList` (§3's known-allergen normalization) before persisting; an all-empty body **deletes** the row (empty profile = no profile — `GET /users/me`'s `diet_profile: null` and `profile_configured: false` mean the same thing). `POST /recipes/:id/cooked` (recipes.ts) writes a `CookedEvent` per call — plain row-per-open, no server dedupe: the reader fires once per dish open, and duplicate rows only thicken a recency signal (a 45-day fetch window bounds the table). `routes/recommendations.ts` mounts both `/recommendations` endpoints; `/internal` fetches profile + visible recipes (own + shared imports) + 45-day cooked events in one `Promise.all` and delegates to the shared pure ranker — the route owns NO ranking logic (ai-pipeline's domain, see its decisions). Both `CookedEvent` and `DiscoverSuggestion` were added to the schema in the same change as development.md §3 (contractual field names), pushed with `pnpm db:push` once for both phases so the Phase 10 agent never touched the schema.
- **Docker image (post-Phase 10, owner request)** — `apps/api/Dockerfile` (build context = repo root, `node:22-bookworm-slim`, glibc — alpine would need a musl `binaryTargets` entry in schema.prisma). Multi-stage: filtered `pnpm install --frozen-lockfile --filter @cookbook/api` → `db:generate` + build inside the container (Linux query engine) → `pnpm --filter @cookbook/api --prod deploy` for a self-contained runtime tree. **`prisma` moved devDeps → dependencies** (the entrypoint needs the CLI). Entrypoint (`apps/api/docker-entrypoint.sh`) runs `prisma db push --skip-generate` on every start — idempotent schema sync for fresh volumes, same tool the dev DB has always used; NEVER `migrate dev`. In-container `DATABASE_URL=file:/data/cookbook.db` (absolute) and `DATA_DIR=/data` on the `cookbook-data` volume — the schema's `file:../data/...` default is a dev-cwd quirk, don't "fix" it in schema.prisma. `WEB_ORIGIN` must list `https://cookbook.<tailnet>.ts.net` explicitly — the private-IP CORS rule doesn't match hostnames. Containers and `pnpm dev` use separate databases.
- **GET /recipes is paginated (2026-09-01, dataset import)** — `?page=` (1-based), `PAGE_SIZE = 24`, response envelope `{items, total, page, page_size, has_more}` (a breaking shape change from the bare array; all web consumers updated in the same change). Non-scoring branch does the title `contains` in Prisma (`skip`/`take` + parallel `count`) — the old whole-table findMany + in-memory filter would pull 13.5k rows per search. Scoring branch (ingredient mode) paginates AFTER the global sort — rank order must not restart per page; the candidate set is bounded by the inverted index. `GET /recipes/favorites` and `GET /ingredients` are unchanged (favorites stay user-scoped and small; the sidebar picker intentionally shows page 1 only).- **Local dataset import (2026-09-01)** — `apps/api/scripts/import-archive.ts` (one-time, idempotent via `dataset://<slug>` source URLs). CSV has embedded newlines inside quoted Instruction fields — parsed with a hand-rolled state machine (no new dep). Shares the public-API pipeline's block mapping/master linking via `services/import-pipeline-helpers.ts` (extracted from import-pipeline.ts so scripts don't import the provider-coupled module). Tagging stays rules-only (no LLM pass exists yet — §6.1 v1), so 13.5k recipes cost zero quota. Images copy into `DATA_DIR/images` as `dataset-<slug>.jpg`.
- **Tier 1 /internal candidates bounded (perf, 2026-09-01, dataset import)** — the route used to hydrate EVERY recipe + ingredient row (13.5k recipes / 144k rows → ~24s per dashboard load, measured). Now: the user's own library in full (personal libraries are small) + the 500 most-recent shared recipes. "Suggested for you" surfaces a handful, so nothing user-visible is lost. Discover's refresh got the same treatment: a random 1000-recipe scan window (not the first 4000 by createdAt — a fixed window would only ever rotate the same 4000) → refresh ≈ 250ms and the whole dataset rotates through over time.
- **Phase 11 chat routes (development.md §14)**: `routes/chat.ts` mounted at `/chat`; `CookingSession`/`ChatMessage` pushed via `pnpm db:push` (Recipe gained the `cookingSessions` back-relation in the same change). Session resolution (design.md §3.3.4): occasions resolve by `occasionKey` ALONE — one transcript per meal occasion, recipe-tab switches keep the conversation, and each turn's optional `recipe_id` both overrides the turn's context and becomes the session's anchor; no-occasion views resolve by `recipeId`. Same-day window = `lastSeenAt >= start of today` (server-local). `fresh: true` on POST /chat/sessions ends today's matching session (sets `endedAt`) and creates a new one — "Start fresh" without a separate PATCH route. Quota path per §14.3: the user message persists FIRST; on `llm_quota_exceeded` the spoken fallback (`CHAT_QUOTA_NOTICE`, shared constant) persists as intent `llm_fallback` and the 429 still returns per §11 — the client renders the same constant, so shown text == persisted text. History for prompt assembly: last 16 rows (≈8 exchanges), `quota_notice` messages filtered out.
